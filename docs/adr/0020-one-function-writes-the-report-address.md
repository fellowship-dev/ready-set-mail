# One function writes our report address into a DMARC record

On the hosted service `applyReportRecord` in `src/hosted/report-address.ts` is the only code that puts our report address into a DMARC record. It builds the record from the **live** record and the person's explicit choice, never from a record a browser sends; it refuses when the live record is not the one the person reviewed; and it connects the domain before it writes the record. The domain page's Connect reports and the first-run review's DMARC step both call it, so the two entry points can no longer write different records for the same domain.

**Consequences**
- **Source of truth.** The live record is read from the domain's Cloudflare zone (`CfClient`, through `tenant.cfFor`) when a connection reaches the zone, because that is the record Apply changes; public DNS (`lookupDmarc`) is read otherwise, and for a name with no record of its own of the zone, the policy it inherits from its organizational domain (`readInherited`, as the first-run plan always did). Public DNS lags Cloudflare, so reviewing public DNS and writing Cloudflare could overwrite a newer record; the review therefore uses Cloudflare's, and after a write the state is `written` ("Written to Cloudflare; public DNS can take a few minutes to show it") until public DNS shows it, derived from live reads, with no new column.
- **The record.** `reviewReportRecord` builds the outcome with the existing builders (`planDmarc` in `src/onboarding/dmarc-plan.ts`: `withReportAddress` and `equivalentRecord`): every tag stays byte for byte except the rua= list, every address stays as published except the one the person chose to replace, the policy never changes. A name with no record of its own gets one that keeps the enforcement in force (`p=none` when nothing applies). Several records, an invalid `p=`, a failed read or a record that would not stay valid: no write, and the true reason.
- **Review and apply.** The review returns the live value (`now`, null when none) and a hash of it and of its source. The apply takes the reviewed hash and the choice (`{ kind: 'add' }` or `{ kind: 'replace', address }`), reads live again and, when it differs, answers `409` `record_changed` with the fresh review; nothing is connected or written. The panel's words are "The record changed since you looked: here it is now" with one Apply.
- **One address-count rule.** RFC 7489 §6.2: "Receivers MAY impose a limit on the number of URIs to which they will send reports but MUST support the ability to send to at least two." RFC 9989 §4.6 and §4.8 and RFC 9990 §3.5 (May 2026, which obsolete 7489) set no number: delivery is "up to the Receiver's limits on supported URIs", evaluated "in the order given". So only the first two addresses were ever honoured by every receiver, and a third may get nothing. Our address is therefore only ever the first or the second address: a record with fewer than two addresses gets ours after them; with two or more, the person picks which of the first two ours replaces, or leaves the record as it is (reports then stay not connected). We never add it third and never reorder anyone else's. The rule lives in `packages/dns-checks/src/dmarc-rua.ts` (`RUA_ADDRESS_LIMIT`, `ruaLimitSentence`: the one wording, used by the panel, the plan and the review). "Keep both and add this address third" is gone. The self-host plan still adds its own reports address as before (`ruaLimit` is off there).
- **Who may.** Before it reads or writes, the function asks what `connectReports` asks: hosted intake on, not hosted records, ownership proven (`isDomainProven`, which covers lost proof and `legacy` rows), the workspace admitted by `HOSTED_CONNECT_REPORTS`. A refusal is `403` with the connect panel's words and nothing is written. Members are refused by the router's read-only rule; delegated keys by `src/access/http-policy.ts`.
- **No other route.** `POST /api/domains/:id/apply-dmarc` and `PATCH /api/domains/:id/dmarc` write only the policy record a person chose. On the hosted service the first refuses (`409`) a record that adds our address or drops a published one (`reportAddressChangeIn`), the second never adds an address of the intake domain (`policyWriteRua`). The setup step on the hosted service no longer builds a record carrying our address and no longer asks `onboarding-status` for one (`offered_rua_address` is gone). The guard in `test/agent-memory/single-sources.lists.ts` ("Writing our report address into a DMARC record") fails on a new caller of the builders that splice the address.
- **Deleted.** the server-side merge into a record the browser sent (the old mergeReportAddress) and the use of `reportAddressForWrite` in `apply-dmarc`; applyViaCloudflare (its test is now one internal `reach`, which also returns the zone); the panel's own record computation in the browser (the apply-dmarc call and the Now/After built from a browser-held plan in `ConnectReports.tsx`); the `limit` outcome of `apply-dmarc` and the "add a third" option.
- Updates the list in ADR 0004: the one new route is `POST /api/domains/:id/report-address/apply`, and the first-run Apply's hosted DMARC write goes through the same function.
- Not covered: the token address of hosted records (`src/hosted/records.ts`, the operator's zone) and TLS-RPT records are other forms and other records (`CONTEXT.md`, "Report address"); the self-host reports address is written as before.
