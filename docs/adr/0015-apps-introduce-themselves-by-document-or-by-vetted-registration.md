# Apps introduce themselves by a published document, or by a registration that is vetted, counted and audited

An assistant can connect in two ways: it publishes a client ID metadata document (Claude, ChatGPT and VS Code prefer this; always on), or it registers itself with `POST /oauth/register` (Cursor and older clients need this; off unless the operator sets `MCP_DCR_ENABLED=1`). Registration stays off in the code's default, and the owner has decided the hosted service switches it on after this change; it is built to be switched on: what a registration may say is checked before the OAuth library stores anything, the instance caps how many arrive and are kept, an app nobody approves is deleted, and each registration, refusal and deletion is audited. The Agents page asks the server what the instance supports and says so.

**Why registration was off.** Not a decision: `1e0c4a08` (2026-10-25, the commit that added the agent OAuth provider) wrote `MCP_DCR_ENABLED` as "explicit legacy client compatibility option; DCR off by default" and `docs/agent-operations.md` repeated it; `19cc246c` (2026-11-13) added the setup-check note "turn it off unless an agent you use needs it". No ADR, no `OPEN.md` row and no owner decision exist; the default was an abuse precaution on an endpoint that stored unbounded, unvetted records. The same switch is on in `scripts/e2e-devbox.sh` (added in `58647dbf`) so the end-to-end spec can register.

**Consequences**
- `/.well-known/oauth-protected-resource` and `/.well-known/oauth-protected-resource/mcp` answer the same RFC 9728 document. The library serves only the path-inserted address (the resource is `<origin>/mcp`), so the root address was answered 404 by the library itself; `withMcpAuthorization` (`src/auth/mcp-issuer.ts`) now rewrites the root request to the path-inserted one, so there is one document and one implementation. Every 401 from `/mcp` carries `WWW-Authenticate: Bearer realm="OAuth", error="invalid_token", resource_metadata="<origin>/.well-known/oauth-protected-resource/mcp"` (`invalidTokenResponse`, `src/mcp/discovery.ts`); the library's own 401s already did, the two this product wrote (the revoked-connection path in `apiHandler`, and `src/mcp/transport.ts`) did not.
- The authorization-server metadata was already complete for Claude's client-document path: `client_id_metadata_document_supported: true`, `"none"` in `token_endpoint_auth_methods_supported`, `code_challenge_methods_supported: ["S256"]`; `registration_endpoint` appears only with the switch. The `global_fetch_strictly_public` compatibility flag (`wrangler.jsonc`) is what turns the client-document support on; `GET /api/agents/status` reports it as `metadata_documents`.
- Registration (`src/mcp/registration.ts`): at most five redirect addresses, each `https`, or `http` on `localhost`, `127.0.0.1` or `[::1]` with any port, without fragment, user name or wildcard; one private-use address is accepted when listed (`cursor://anysphere.cursor-mcp/oauth/callback`, which the OAuth library never sends a code to). A name (`src/mcp/client-names.ts`) is NFKC-normalised plain text of at most 80 characters, no markup characters, no web address, no mixing of alphabets (Latin with Cyrillic or Greek) and no claim to be verified, official, certified or approved (words or ✓ ✔ ✅ marks), or it is refused; one that is or contains a reserved name (Claude, Anthropic, ChatGPT, OpenAI, Cursor, VS Code, Copilot, GitHub, Gemini, Google, Microsoft, Ready Set Mail and a few more, compared after folding case, accents and look-alike letters) is accepted but not stored, so real Cursor and Claude Code registrations keep working and no self-registered app can present a famous name. None given is shown by its address. Public clients only; the two grants; the `code` response. A registration is refused with an RFC 7591 error body (`invalid_redirect_uri`, `invalid_client_metadata`), 413 when over 16 KiB.
- Limits (`src/mcp/registration.ts`, each with its basis): 10 a minute per address (the existing `AUTH_LIMITER` budget); **20 a day per address** (`MCP_DCR_ADDRESS_DAILY_LIMIT`: a person registers an assistant once per install, so a team behind one address needs a handful, and an IPv6 address counts as its /64); **2,000 a day for the whole instance** (`MCP_DCR_DAILY_LIMIT`: 100 addresses at their own limit, a backstop sized so that one address can use at most 1% of it; a refused address spends none of it); **5,000 stored apps**, waiting and approved (`MCP_DCR_MAX_CLIENTS`: about 5 MB of KV records). Over a daily count the answer is 429 with `Retry-After`. At the ceiling the oldest app nobody approved is evicted to make room; only when every stored app is approved is the answer 503 `temporarily_unavailable`.
- Expiry: an app nobody approved is deleted **24 hours** after it registered (`MCP_DCR_UNUSED_HOURS`: long enough to sign in and approve the same or the next day). The waiting apps are listed in a registry (`globalQueries.agentClients`, rows of `auth_rate_limits` under `agent-client:<id>`, which the generic rate-limit sweep leaves alone) that approving an app removes it from, so what is listed is exactly what may be deleted. Each registration first deletes up to 10 expired apps, and the daily lifecycle job (`0 4 * * *`, `runDataLifecycle`, which runs on every deployment) deletes oldest first in batches until none are left or one invocation's budget (800 deletions, 25 s) is used, so the store drains at least as fast as it fills. An approved app is never deleted by it: its refresh tokens need its registration. No migration.
- A person is never led by a name the app chose. The approval page and Settings → Agents lead with the address that is verifiable (the publisher's host for an app with a client document, otherwise the address the app sends the person back to, or "an app on this computer" for a loopback address) and show the name as "calls itself". Nothing is pre-ticked for a self-registered app; a client-document app gets only the two read permissions pre-ticked, never a write permission.
- A refresh token is used once (OAuth 2.1, draft-ietf-oauth-v2-1 section 4.3.1; RFC 9700 section 4.14.2): the library accepts the previous one for one more use; `src/mcp/refresh-replay.ts` refuses a replaced token, revokes the grant and disables the approval, so a leaked old token ends the connection and the person approves again. A client that retries a refresh it did not hear the answer to loses its connection too; that is the rule's cost.
- A client document is fetched without following redirects (draft-ietf-oauth-client-id-metadata-document: MUST NOT), by making every request of the library (recognised by its User-Agent) with `redirect: "manual"` (`src/mcp/client-document-fetch.ts`); private addresses stay blocked by `global_fetch_strictly_public`, and the library's 5 KB and 10 s limits stay.
- An approval page reached while signed out links to "Sign in and continue", which carries the request through sign-in (`?continue=` with this endpoint's own path and query only, kept in the tab; `web/src/lib/resume.ts`), so the person returns to the page and not to the dashboard. The approval form's buttons sit in a bar that stays at the bottom of the screen.
- Audit: `agent.client_registered`, `agent.client_registration_refused` (with the reason) and `agent.client_expired`, written with `logAudit` to the instance's own scope (`IMPLICIT_WORKSPACE_ID`, actor type `system`), because a registration has no person and no workspace. No address of the caller is stored. A request over the per-address budget is answered 429 by the limiter and is not audited, so an attacker cannot fill the log.
- An authorization link that cannot go on (unknown or unreadable `client_id`, a redirect address that was not registered, an incomplete link, an expired or reused consent page) renders a page in the product's style with a way back to Agents (`renderConsentProblem`), signed in or not, and never redirects. Machine endpoints (`/oauth/token`, `/oauth/register`, `/mcp`) keep JSON errors.
- A connection record keeps how the app is led with (`name`), what it calls itself (`calledItself`) and whether it is verified (a client-document client is verified by its host; a registered one is "Not verified"). The list in Settings → Agents reads what it can reach from the live grants. Last use is written at most once every five minutes (`AGENT_USE_WRITE_SECONDS`).

**Decisions**
1. The owner decided registration is switched on for the hosted service after this change (nothing live is touched by it); the code's default stays off, which is right for self-host.
2. The limits and the 24-hour expiry above, with their basis.
3. A registration that omits `token_endpoint_auth_method` is stored as a public client (`none`); a confidential client is refused.
4. The listed-only `cursor://anysphere.cursor-mcp/oauth/callback` address is allowed (the OAuth library's own documentation names it among Cursor's registered callbacks). Any other custom scheme is refused.
5. A registration with `<`, `>` or `&` in its name is refused rather than cleaned; a reserved name is withheld, not refused.
6. A refused or limited registration is audited in the instance scope; per-minute limiter refusals are not.
7. Not built: per-client allow lists, operator approval of each registration, the registration management endpoints of RFC 7592, confidential clients.
