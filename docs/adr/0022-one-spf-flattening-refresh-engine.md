# SPF flattening has one refresh engine, and it resolves the stored original

SPF flattening is resolved by `flattenFromSource` in `packages/dns-checks/src/spf-flatten.ts` and written, refreshed and undone by `src/spf/refresh.ts`, for self-host, hosted, the routes and the daily job alike. The refresh always resolves **the original record** stored when flattening was turned on, never the record published now: once flattened, the published record has no includes left, so re-walking it (what the old `0 10` job did) can never see a provider change.

**Why**
- The old job (the Cloudflare flattener module) re-read the flat record, so provider IPs never arrived, yet it logged "updated" and wrote an audit row every day; the hosted design (a stored-source resolver next to the hosted jobs) resolved from a stored source and was right. They are one implementation now: the hosted records path calls the same engine with its own target, and the old modules are deleted.
- Selective flattening: measured today from real DNS, flattened `ip4`/`ip6` terms only: `_spf.google.com` 233 bytes, `spf.protection.outlook.com` 249, `sendgrid.net` 347, `mailgun.org` 483, `amazonses.com` 268, Google and Outlook together 458. A record should stay under 450 bytes (RFC 7208 section 3.4) and a domain over 10 lookups usually has three or more providers, so refusing a result over 450 would make the feature useless for the people who need it. The engine inlines only as many top-level includes as it takes to land within 10 lookups (counting what the kept includes cost) and 450 bytes: the fewest inlined, then the fewest bytes, every refresh. No choice fits: one plain sentence, nothing written. Chained records are not used (a second managed name per domain; `src/dns/write-policy.ts` forbids `_`-prefixed names and ADR 0004 would need extending).
- Never widen: only `+` ip terms of an included record are inlined; an include with any other qualified term, a `+all` or a macro in a copied term stays an include; the original's `all` is kept (none stays none). A truncated DNS answer is a failed resolution.

**Consequences**
- The refresh writes only when the resolved record differs (order, case, spacing aside), and only after reading the record in Cloudflare: a record that is not the value last written was changed outside the app and is never overwritten (problem state, Review). Turning off never writes over an outside edit.
- Writes are claim-first compare-and-set (`spf_flatten_config.revision`, migration 0021): two runs, or a run during turning off, never write twice or resurrect a turned-off row.
- The job runs on `0 11 * * *` in both modes (it was `0 10`; an older `0 10` trigger is answered by the same function). **Basis (wiki L-080): the hosted service runs `0 4` and `0 11` because they "write no DNS". That stays true while `HOSTED_SPF_FLATTENING` is off (the default): the job finds no workspace it may refresh. The owner turning it on for a workspace is what makes `0 11` write DNS on hosted.** The alternative, turning on the held `0 10` for this job alone, is a one-line change in `src/cron.ts`.
- This narrows the automatic-write bullet of ADR 0004 (the flattened record, now at 11:00 UTC); it adds no new kind of automatic write (a record a person turned on).
- The rule for what may be written (a removal waits, ADR 0024) is one function, `decideSpfWrite` in `src/spf/refresh.ts`, used by the customer's refresh and by the hosted records' refresh (`src/hosted/cron.ts`, state in `hosted_domains.spf_state`); the original is rewritten only by the owner's choice after an outside edit ([ADR 0025](0025-the-owner-may-adopt-an-outside-edit-as-the-new-original.md)). Two guards fail a second flattener: one by name (`test/agent-memory/single-sources.lists.ts`, "SPF flattening") and one by what a module does (`test/agent-memory/single-sources.behaviour.test.ts`). A removal is held for a second look: [ADR 0024](0024-a-refresh-never-removes-an-address-on-first-sighting.md). Details, limits and the job: `docs/spf-flattening.md`.
