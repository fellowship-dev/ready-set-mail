# Apps introduce themselves by a published document, or by a registration that is vetted, counted and audited

An assistant can connect in two ways: it publishes a client ID metadata document (Claude, ChatGPT and VS Code prefer this; always on), or it registers itself with `POST /oauth/register` (Cursor and older clients need this; off unless the operator sets `MCP_DCR_ENABLED=1`). Registration stays off in the code's default, and the owner has decided the hosted service switches it on after this change; it is built to be switched on: what a registration may say is checked before the OAuth library stores anything, the instance caps how many arrive and are kept, an app nobody approves is deleted, and each registration, refusal and deletion is audited. The Agents page asks the server what the instance supports and says so.

**Why registration was off.** Not a decision: `1e0c4a08` (2026-10-25, the commit that added the agent OAuth provider) wrote `MCP_DCR_ENABLED` as "explicit legacy client compatibility option; DCR off by default" and `docs/agent-operations.md` repeated it; `19cc246c` (2026-11-13) added the setup-check note "turn it off unless an agent you use needs it". No ADR, no `OPEN.md` row and no owner decision exist; the default was an abuse precaution on an endpoint that stored unbounded, unvetted records. The same switch is on in `scripts/e2e-devbox.sh` (added in `58647dbf`) so the end-to-end spec can register.

**Consequences**
- `/.well-known/oauth-protected-resource` and `/.well-known/oauth-protected-resource/mcp` answer the same RFC 9728 document. The library serves only the path-inserted address (the resource is `<origin>/mcp`), so the root address was answered 404 by the library itself; `withMcpAuthorization` (`src/auth/mcp-issuer.ts`) now rewrites the root request to the path-inserted one, so there is one document and one implementation. Every 401 from `/mcp` carries `WWW-Authenticate: Bearer realm="OAuth", error="invalid_token", resource_metadata="<origin>/.well-known/oauth-protected-resource/mcp"` (`invalidTokenResponse`, `src/mcp/discovery.ts`); the library's own 401s already did, the two this product wrote (the revoked-connection path in `apiHandler`, and `src/mcp/transport.ts`) did not.
- The authorization-server metadata was already complete for Claude's client-document path: `client_id_metadata_document_supported: true`, `"none"` in `token_endpoint_auth_methods_supported`, `code_challenge_methods_supported: ["S256"]`; `registration_endpoint` appears only with the switch. The `global_fetch_strictly_public` compatibility flag (`wrangler.jsonc`) is what turns the client-document support on; `GET /api/agents/status` reports it as `metadata_documents`.
- Registration (`src/mcp/registration.ts`): at most five redirect addresses, each `https`, or `http` on `localhost`, `127.0.0.1` or `[::1]` with any port, without fragment, user name or wildcard; one private-use address is accepted when listed (`cursor://anysphere.cursor-mcp/oauth/callback`, which the OAuth library never sends a code to). A name (`src/mcp/client-names.ts`) is NFKC-normalised plain text of at most 80 characters, no markup characters, no web address, no mixing of alphabets (Latin with Cyrillic or Greek) and no claim to be verified, official, certified or approved (words or ✓ ✔ ✅ marks), or it is refused; one that is or contains a reserved name (Claude, Anthropic, ChatGPT, OpenAI, Cursor, VS Code, Copilot, GitHub, Gemini, Google, Microsoft, Ready Set Mail and a few more, compared after folding case, accents and look-alike letters) is accepted but not stored, so real Cursor and Claude Code registrations keep working and no self-registered app can present a famous name. The fact is kept (`count` 2 on the app's waiting row, then `nameWithheld` on the approved connection), so the approval page and Settings → Agents say "It used the name of a well-known app, so the name is not shown: only the address below is known." and keep "It gave no name." for an app that gave none. None given is shown by its address. Public clients only; the two grants; the `code` response. A registration is refused with an RFC 7591 error body (`invalid_redirect_uri`, `invalid_client_metadata`), 413 when over 16 KiB.
- Limits (`src/mcp/registration.ts`, each with its basis): 10 a minute per address (the existing `AUTH_LIMITER` budget); **20 a day per address** (`MCP_DCR_ADDRESS_DAILY_LIMIT`: a person registers an assistant once per install, so a team behind one address needs a handful, and an IPv6 address counts as its /64); **2,000 a day for the whole instance** (`MCP_DCR_DAILY_LIMIT`: 100 addresses at their own limit, a backstop sized so that one address can use at most 1% of it; a refused address spends none of it); **5,000 apps in use** (`MCP_DCR_MAX_CLIENTS`: about 5 MB of KV records): the registered apps with a live connection, plus the unapproved ones still inside their 24 hours. Over a daily count the answer is 429 with `Retry-After`. At the ceiling the oldest app nobody approved is evicted to make room (expired ones first; they count for nothing, so the count is taken again).
- Expiry: an app nobody approved is deleted **24 hours** after it registered (`MCP_DCR_UNUSED_HOURS`: long enough to sign in and approve the same or the next day). The waiting apps are listed in a registry (`globalQueries.agentClients`, rows of `auth_rate_limits` under `agent-client:<id>`, which the generic rate-limit sweep leaves alone) that approving an app removes it from, so what is listed is exactly what may be deleted. Each registration first deletes up to 10 expired apps, and the daily lifecycle job (`0 4 * * *`, `runDataLifecycle`, which runs on every deployment) deletes oldest first in batches until none are left or one invocation's budget (800 deletions, 25 s) is used, so the store drains at least as fast as it fills. A batch is **90** apps at most: D1 allows 100 bound values in one statement ("too many SQL variables"), a batch of 100 failed the whole job once 97 had expired, and the in-memory database the tests use allowed it. The test database now refuses what D1 refuses (`packages/db/src/testing/d1-sqlite.ts`), and every `IN (...)` list the clean-up binds goes through `inChunks` (`packages/db/src/queries/in-list.ts`). The job goes on past a page in which every app turned out to be approved (it removes their waiting rows) and stops only when none are due. An approved app is never deleted by it: its refresh tokens need its registration.
- A person is never led by a name the app chose. The approval page and Settings → Agents lead with the address that is verifiable (the publisher's host for an app with a client document, otherwise the address the app sends the person back to, or "an app on this computer" for a loopback address) and show the name as "calls itself". **Nothing is pre-ticked for any app**, verified or not (the owner's decision: nothing that grants write is pre-ticked, and one rule is simpler than two): the page says, above the first choice, "Nothing is ticked yet: it gets only what you tick, until the date you pick", and an approval with nothing chosen is answered "Choose at least one thing the app may do." Earlier a client-document app had `resources:read` and `reports:read` ticked, and a verified app with one domain had that domain ticked.
- **A refresh token is used once, with a 30-second grace window** (`src/mcp/refresh-replay.ts`, the one place that decides this). A public client has nothing but rotation to make a stolen token useless: OAuth 2.1 (draft-ietf-oauth-v2-1 section 4.3.1) requires sender-constrained tokens or rotation for public clients, and says that on presentation of an invalidated refresh token the server revokes the active refresh token and the grant; RFC 9700 section 4.14.2 has the same reuse rule (https://www.rfc-editor.org/rfc/rfc9700#section-4.14.2). The first version of that rule ended the connection for two tool calls that both found the access token expired and both refreshed with the same token (7 of 7 trials), and for a client that retries a refresh whose answer was lost (draft section 4.3.3: a lost response can leave the client with only an invalidated token). The rule now: within **30 seconds** after a refresh token R was first used, presenting R again returns the SAME new tokens the first use produced (the access token's `expires_in` says how long it has left), not a second rotation; after 30 seconds, or presenting any older token (two or more rotations back), ends the connection as before (the grant, every token of it and the approval in Settings, audited as `agent.refresh_token_replayed`). Basis: Okta's "Grace period for token rotation" has a default of 30 seconds and a range of 0 to 60 (https://developer.okta.com/docs/guides/refresh-tokens/main/); Auth0's "Rotation Overlap Period" (`leeway`, in seconds) lets only the previous token be reused within it and treats an older one as a breach (https://auth0.com/docs/secure/tokens/refresh-tokens/configure-refresh-token-rotation). 30 seconds covers parallel tool calls (sub-second) and one retry after a lost response, while a stolen copy stays useful for at most 30 seconds and only to receive the tokens the real client already holds.
  Atomic on D1, because KV is not: a table `refresh_rotations` (migration `migrations/0021_refresh_rotations.sql`, additive) holds a row per used token, keyed by the token's SHA-256 (the token is never stored): the grant, the time of the first use, `pending` or `done`, and the answer encrypted with AES-GCM under a key derived (HKDF-SHA-256) from the presented token itself, so the row is useless without it. The first request inserts the row (`INSERT … ON CONFLICT DO NOTHING`; one request wins), lets the library rotate, and stores the sealed answer. Requests that lose the insert read the row every 100 ms for up to 5 seconds and return the winner's answer. If the winner fails, its row is dropped and the others get 503 `temporarily_unavailable` with `Retry-After: 1`, never a revocation; a row left `pending` by a request that died is taken over after 10 seconds. A token whose row exists and is older than 30 seconds, or that is not the grant's current or previous token, ends the connection. Rows are deleted by the daily clean-up once older than the refresh token's life (30 days). Cost: the same stored answer is also what a thief who has the token within 30 seconds receives; it is the same answer the real client received.
- A client document is fetched without following redirects (draft-ietf-oauth-client-id-metadata-document: MUST NOT), by making every request of the library (recognised by its User-Agent) with `redirect: "manual"` (`src/mcp/client-document-fetch.ts`); private addresses stay blocked by `global_fetch_strictly_public`, and the library's 5 KB and 10 s limits stay.
- An approval page reached while signed out links to "Sign in and continue", which carries the request through sign-in (`?continue=` with this endpoint's own path and query only, kept in the tab; `web/src/lib/resume.ts`), so the person returns to the page and not to the dashboard. The approval form's buttons sit in a bar that stays at the bottom of the screen.
- **Audit, and what it keeps** (`logAudit`, `audit_log`, deleted after `RETENTION_AUDIT_DAYS`, **365 days** by default, by the daily retention job; a deleted person's email is removed from their entries and the entries stay). Instance scope (`IMPLICIT_WORKSPACE_ID`, actor type `system`, because a registration has no person and no workspace): `agent.client_registered` (app id, name, redirect hosts), `agent.client_registration_refused` (reason, redirect hosts), `agent.client_expired` and `agent.client_evicted` (app id, when it registered). In the connection's workspace: `agent.connection_approved` (the person's id and email, the connection id, how the app was led with, the app id, the permissions, how many domains, the days), `agent.connection_revoked` (the person, the connection), `agent.connection_removed` (system: the connection that the clean-up deleted, why: revoked or expired, its app id, whether the app was deleted with it), `agent.refresh_token_replayed` (system: the connection that was ended). In the instance scope too: `agent.approval_limit_reached` (the person, which limit). No address of the caller is stored. A request over the per-address budget is answered 429 by the limiter and is not audited, so an attacker cannot fill the log. So when a connection's record is deleted a year of its history remains: who approved what, when, and that it was removed.
- An authorization link that cannot go on (unknown or unreadable `client_id`, a redirect address that was not registered, an incomplete link, an expired or reused consent page) renders a page in the product's style with a way back to Agents (`renderConsentProblem`), signed in or not, and never redirects. Machine endpoints (`/oauth/token`, `/oauth/register`, `/mcp`) keep JSON errors.
- A connection record keeps how the app is led with (`name`), what it calls itself (`calledItself`) and whether it is verified (a client-document client is verified by its host; a registered one is "Not verified"). The list in Settings → Agents reads what it can reach from the live grants. Last use is written at most once every five minutes (`AGENT_USE_WRITE_SECONDS`).
- **Ended connections are deleted, and no account can use up the room.** A connection is live while its principal is not disabled (revoked in Settings) and its record has not ended. The ceiling counts live registered apps and unapproved ones inside their time, so a revoke or an end date gives the place back at once, and an app that publishes a client document (not stored by us) takes none. The daily clean-up deletes the record, the principal (its grants go with it) and the registered app when no record of it remains, **7 days** after the connection ended (`CONNECTION_RETENTION_DAYS`, `src/mcp/connection-limits.ts`): the day's approval limit below needs the last 24 hours of records, Settings → Agents can still show what was revoked this week, and the audit log (above) keeps the history for a year. Batches of 50 records, at most 400 records and 200 apps a run, 25 seconds.
- **Per-person and per-workspace limits on approvals** (`approvalLimitReached`; hypotheses, nothing measured yet; the signal is the `agent.approval_limit_reached` entries and what support hears): **20 live apps per person** (a person uses a handful of assistants, a few installs of each), **50 live apps per workspace** (a few people with theirs), **20 approvals per person in 24 hours**, revoked ones included (connecting again after a link expired, trying an app: a few a day; it is what stops an approve-and-revoke loop). Raise a number when people who use their apps hit it; lower the day limit if the loop shows up in the audit log. When a limit is reached the approval page (shown before the form for the person limits, on Allow for the workspace) says in plain words which one and what to do: revoke one you no longer use in Settings → Agents, ask a teammate to, choose another workspace, or try tomorrow; nothing is shared. Soft: two approvals at the same instant can both pass. The same on the hosted service and self-hosted.
- **Registration is never refused for good.** The oldest unapproved app is evicted first. A 503 with `Retry-After: 3600` is answered only while the ceiling is full of live approved apps, which with 20 per person takes at least 250 distinct accounts (5,000 ÷ 20), each keeping their apps connected; it clears as soon as one person revokes or one connection reaches its end date (the count is of live connections, so it does not wait for the clean-up).

**Decisions**
1. The owner decided registration is switched on for the hosted service after this change (nothing live is touched by it); the code's default stays off, which is right for self-host.
2. The limits and the 24-hour expiry above, with their basis.
3. A registration that omits `token_endpoint_auth_method` is stored as a public client (`none`); a confidential client is refused.
4. The listed-only `cursor://anysphere.cursor-mcp/oauth/callback` address is allowed (the OAuth library's own documentation names it among Cursor's registered callbacks). Any other custom scheme is refused.
5. A registration with `<`, `>` or `&` in its name is refused rather than cleaned; a reserved name is withheld, not refused.
6. A refused or limited registration is audited in the instance scope; per-minute limiter refusals are not.
7. Not built: per-client allow lists, operator approval of each registration, the registration management endpoints of RFC 7592, confidential clients.
8. The refresh grace window is 30 seconds (basis above); implemented in D1, migration 0021.
9. The limits of 20 / 50 / 20 and the 7-day retention are the implementer's hypotheses; the owner confirms or changes them.
10. Nothing is pre-ticked for any app (owner).
11. Approvals, revocations and removals of a connection are audited (they were not, so the history the clean-up leaves behind did not exist).
12. An app with a client document is not counted against the registration ceiling: the ceiling protects what we store, and we do not store it.
13. Other queries that can bind more than 100 values on D1 are listed in the pull request as a follow-up; only the ones this change touches were fixed.
