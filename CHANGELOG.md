# Changelog

All notable changes to Ready Set Mail are recorded here, newest first. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/).
How releases are cut and how each pull request adds its line under `[Unreleased]`: [docs/releasing.md](docs/releasing.md).

## [Unreleased]

### Changed

- **MTA-STS works on the hosted service, and is one path for hosted and self-host.** Turning it on from the domain page no longer answers "connect Cloudflare first" when Cloudflare is connected. The three records go into your own zone (through your Cloudflare connection, or shown for you to add), the policy is served by this Worker on `mta-sts.<your domain>` (on the hosted service through a Cloudflare for SaaS custom hostname), it always starts in testing, and TLS reports arrive at the shared address `tls-rpt@<INTAKE_DOMAIN>`. The `_mta-sts` id is published last, once the policy is served; the stored policy changes before the id does. Enforce needs 7 days in testing and the TLS reports to show senders could use TLS (CHANGELOG 1.2.0 promised the 7 days; nothing checked it); Disable is offered in testing, and once senders that fetched an enforce policy no longer hold it; a domain that already has an `_mta-sts` or `_smtp._tls` record is refused instead of overwritten; removing a domain, losing its proof or an eviction now removes what MTA-STS made (before, the records were left behind, issue #166). Every other path on an `mta-sts.*` hostname is a 404. The hosted operator settings are `POLICY_HOST_ZONE`, `POLICY_HOST_TARGET`, the secret `POLICY_HOST_TOKEN` and `MAX_POLICY_HOSTS` ([docs/hosted.md](docs/hosted.md), [ADR 0015](docs/adr/0015-mta-sts-customer-zone-records-and-saas-policy-host.md), migration `0019_mta_sts_hosted.sql`).
- **Breaking (hosted API): hosted records no longer host MTA-STS.** `POST /api/domains/:id/hosted` with `mta_sts: true` answers 400 (turn MTA-STS on from `/api/domains/:id/mta-sts`), the `mta-sts.<id>.h.<zone>` records and the hosted-id policy host are gone, and a domain with hosted records cannot use MTA-STS. Hosted records that were made with MTA-STS are still removed with the domain's hosted records. Self-host is unaffected.

- **Hand-off resend keeps the working link until the new one exists; waits over an hour are said in hours; more free-mail providers are recognised; the hand-off email frames the workspace name.** "Get a new link" now checks the limits first and revokes the old link only after the new invitation was issued (and, when we email it, sent), so a resend at the daily cap or a failed send no longer leaves the invited person with no working link (a resend does not count as a sixth open hand-off). A code-mail wait of more than an hour reads "in 22 hours", not "in 1320 minutes". Free-mail detection (`isFreeMailDomain`, `src/auth/names.ts`) matches the hotmail, outlook, live, yahoo and gmx families with country variants (hotmail.co.uk, live.com.mx, yahoo.co.jp, gmx.at) plus mail.ru, rocketmail.com and protonmail.ch, never `live.example-corp.com` or `outlookdesign.com`. The hand-off email no longer puts the workspace name in its main sentence: it says `They call the workspace "<name>".` (40 characters, only when the domain is proven), like `They call themselves "<name>".`. The flow check (`scripts/check-flows.mjs`) keeps a walk record fresh until a file the flow covers changes after the walked commit, instead of requiring it to be walked after the base commit's time. No migration.
- **Hosted sign-up is three screens, shaped like PostHog's.** S1 asks for the email and a password and sends the code on Continue (the bot check runs unseen and shows only if Cloudflare needs a click); S2 "Tell us about yourself" (your name, organization name, whose email you are setting up, an optional role, where you heard about us) is filled in while the email travels; S3 "Check your inbox" is one big code input that submits at the sixth digit, with "Not seeing it?" for a new code and "Wrong address? Start over". The URL holds the step (`#/signup`, `#/signup/about`, `#/signup/code`) and a returning person lands on the screen the server's pending attempt says. S2's answers are held server-side with the pending attempt and applied once, when the code is right and the account is created (no account exists before the code; no migration). The first workspace is named with the organization name; an agency's organization name is its own name (the workspace switcher's heading) and its first workspace is named after the first client domain. Code limits, lifetime and anti-enumeration are unchanged. See [docs/hosted.md](docs/hosted.md#sign-up-screens).
- **One screen for the first domain, a review before anything is written, and a first-day card (hosted).** After sign-up, S4 asks which domain you send email from (an agency: its first client's), reads public DNS in one line and offers Connect Cloudflare when its name servers are Cloudflare's (or "Continue with <account>" when a connection already holds the zone); any other host, or one we cannot tell, goes to the existing record screen with the provider named. After Cloudflare returns, a review shows what is there now and what Apply would write (the DMARC record with the hosted report address where reports are admitted, else without one, said plainly), then the dashboard. The "Get to your first answer" stepper is replaced by a first-day card: waiting for the report address, "Your first reports are on their way", "No reports yet" after 3 days, or the first reports. Self-host keeps its home-base setup. See [docs/hosted.md](docs/hosted.md#first-run-hosted-s4-c2-and-the-first-day-card).
- **Hand setup to a teammate (hosted).** From the first screen or the review, an owner can invite a teammate as an admin to finish one domain: a fixed-wording invitation by email, a join page that says what to finish, then straight to that domain's first screen; the owner's dashboard shows who is finishing and where it stands until the records are live, with "Resend invitation" and "Finish it myself". It uses the existing admin invite (no migration). See [docs/hosted.md](docs/hosted.md#hand-setup-to-a-teammate).
- **No red on a domain's first day (hosted and self-host).** Until a domain's first report arrives, and for its first 72 hours, the overview row says "Waiting for reports" in the neutral state, with what is missing as "to fix after reports", instead of "Needs attention". Real failures (a name that does not resolve, DNS checks that fail, a lapsed proof) keep their words; the domain page is unchanged.
- **Hand-off invitations name the sender by their verified address, and name a domain only when it is proven (hosted).** The subject and body say who asked by email address; the display name appears once, in the body, as "They call themselves …" (40 characters). The domain and workspace are named only when that domain is proven in the workspace, else "a domain". We send the invitation only when it is safe: the teammate is at the sender's own email domain and that is not a free-mail domain, or a domain in the workspace is proven (`mayEmailHandoff`, `src/team/handoff.ts`). In every other case nothing is refused and nothing is emailed: the invite and the hand-off exist as usual and the owner gets the link to send themselves (`{ token, url, emailed: false }`; "Copy link" on the same screen). The daily cap is per account as well as per workspace (10 each). No migration.
- **Sign-up code mail: 5 an hour and 10 a day per address (was 2 and 4), and the wait is the real time left (hosted).** An honest sign-up (code expired, password again, "Send a new code", "Start over") could hit the old cap; two attacker sign-ups for an address could block its owner. Per-IP limits, the bot check, 5 tries per code and the 10-minute lifetime are unchanged. After a code is used up or expired, "Send a new code" shows right under the message. See ADR 0001 (amendment).
- **First run, round 3 (hosted).** The domain S4 was given is held on the server, so a second browser after Cloudflare's Allow names it (not the first imported zone); S2's answers survive "Start over" in this tab (never the password); S4's result is one line; fewer repeated words on the Cloudflare path; the first-day card appears only for a domain added in the last 14 days, so an existing account keeps the overview it had. Walk records may carry a tag, `<date>-<id>.<tag>.md`.
- **An agency's placeholder workspace name is a flag, not the words "New client" (hosted).** A workspace setting (`name_is_placeholder`, existing `settings` table, no migration) marks the first workspace of an agency sign-up; only a flagged workspace is named after its first client domain, and renaming it yourself clears the flag.
- **The first-run screens, second pass.** The invitee's code screen is the same one as sign-up's; the first-day card is the first thing on the dashboard and level ladders wait for the first report; S4 checks a domain from the website checker on arrival, opens Cloudflare's consent directly, and uses the width of a wide screen; the record-adding path looks for the record by itself (every 15 seconds for 10 minutes while the page is open, then every minute); a cancelled Cloudflare consent returns to S4 with a plain sentence; a sign-up that timed out says so and keeps the email; the app root resumes a sign-up in progress; an agency's connection adds only the client domain being set up; after Apply the dashboard shows no toast that repeats the card (only one when Cloudflare could not read the write back), and while the card waits for the report address the long "Reports not connected yet" block is not shown beside it.
- **The new sign-up screens are counted in hosted product analytics (categories only).** `Signup Profile Saved` (the fork answer, the role, and whether "heard about" was filled, never its text), the resend counts as `Signup Code Sent` (resend), S1 sends the website link's `src` and `from_checker`, and the S4 choice is `Setup Path Chosen` (`POST /api/onboarding/setup-path`, and the hand-off invitation). ADR 0014 records that an agency's Cloudflare connection imports only the client's zone.
- **The code email is HTML and plain text**, with the wordmark as text, one sentence and the code in large selectable digits; Reply-To is `MAIL_REPLY_TO` when set. The subject is unchanged.

## [2.0.0] - 2026-11-15

2.0 rebuilds Ready Set Mail (formerly Inbox Angel) around workspaces, a new dashboard, a one-command installer and agent access. <!-- @legacy-name: the product's earlier name -->

### Upgrading from 1.x

**A 1.x installation (v1.2.0 or earlier) cannot be upgraded in place.** The database migration history was squashed into a new baseline, so `npm run migrate` fails against a 1.x database and there is no step that converts one into the other. Install 2.0 next to the old installation and move over:

1. Keep the old Worker running and export its database: `npx wrangler d1 export inbox-angel --remote --output v1-backup.sql` (use your database's name if you changed it). Keep that file: it is the only copy of your 1.x report history. <!-- @legacy-name: the 1.x database name -->
2. Install 2.0 under a new name: `npm run setup -- --name <new name>` (see "Self-hosters: what changes" below).
3. Open the setup link it prints, create the owner account, add your domains again and point each domain's DMARC `rua` at the new instance's report address.
4. When reports arrive at the new instance, remove the old Worker and its database.

What does not carry over: **report history** (it stays in your export, a SQL dump you can load into SQLite), users and invitations, settings, the audit log and alert subscriptions; all start fresh in the new database. Old `ia_…` API keys do not work in 2.0: issue new `ias_…` credentials. The full procedure: [packages/db/UPGRADING.md](packages/db/UPGRADING.md#installs-from-v120-and-earlier-cannot-be-upgraded-in-place).

### Self-hosters: what changes

- **Install with `npm run setup`.** It creates the D1 database and the `OAUTH_KV` namespace, generates the secrets, deploys the Worker and prints a signed setup link that makes you the owner (valid once, for 15 minutes; `npm run setup -- --new-link --name <name>` prints a fresh one). `npm run setup -- --uninstall --name <name>` removes what it created after exporting the database. The Deploy to Cloudflare button is gone. ([#160](https://github.com/fellowship-dev/ready-set-mail/pull/160), [#164](https://github.com/fellowship-dev/ready-set-mail/pull/164))
- **New settings.** `BOOTSTRAP_SECRET` (the private first-owner proof, at least 32 characters), `BETTER_AUTH_URL` (the instance's HTTPS origin), the `OAUTH_KV` namespace (agent sign-in) and `TOKEN_ENCRYPTION_KEY` (to connect Cloudflare from the dashboard). The installer sets all four and keeps copies of the secrets in `~/.config/ready-set-mail/<name>/`. The rate-limit bindings `AUTH_LIMITER`, `API_LIMITER`, `DNS_PREVIEW_LIMITER`, `MCP_LIMITER`, `OAUTH_TOKEN_LIMITER` and `MCP_ANON_LIMITER` come from `wrangler.jsonc`; your own ids live in the git-ignored `wrangler.local.jsonc`. ([#101](https://github.com/fellowship-dev/ready-set-mail/pull/101), [#113](https://github.com/fellowship-dev/ready-set-mail/pull/113), [#130](https://github.com/fellowship-dev/ready-set-mail/pull/130), [#145](https://github.com/fellowship-dev/ready-set-mail/pull/145), [#160](https://github.com/fellowship-dev/ready-set-mail/pull/160))
- **Migrations are explicit.** The Worker no longer changes its own schema: run `npm run migrate` (`npm run deploy` runs it for you) before the new Worker serves traffic. Until the newest migration is recorded the Worker answers 503 and refuses inbound report mail so senders retry. ([#107](https://github.com/fellowship-dev/ready-set-mail/pull/107), [#115](https://github.com/fellowship-dev/ready-set-mail/pull/115))
- **Renamed resources.** Inbox Angel is now Ready Set Mail: the Worker is `ready-set-mail-worker` in `wrangler.jsonc` (the installer names it after `--name`, default `ready-set-mail`) and the D1 database is `ready-set-mail`. Domain ownership TXT proofs and the setup header from before the rename are still accepted. ([#108](https://github.com/fellowship-dev/ready-set-mail/pull/108), [#149](https://github.com/fellowship-dev/ready-set-mail/pull/149)) <!-- @legacy-name: the product's earlier name -->
- **Retired keys.** `ia_…` API keys and the `API_KEY` setting no longer authenticate; issue finite `ias_…` credentials in Settings instead. ([#101](https://github.com/fellowship-dev/ready-set-mail/pull/101), [#130](https://github.com/fellowship-dev/ready-set-mail/pull/130))
- **Cloudflare connections.** Connect Cloudflare from the dashboard with a pasted token, or with OAuth when the instance has an OAuth client configured; tokens are stored encrypted. A server-wide `CLOUDFLARE_API_TOKEN` secret still works for the default workspace. ([#113](https://github.com/fellowship-dev/ready-set-mail/pull/113), [#163](https://github.com/fellowship-dev/ready-set-mail/pull/163))
- **Scheduled jobs.** Five cron triggers: daily DNS re-check and change alerts (08:00 UTC), the Monday digest (09:00), SPF flattening refresh (10:00), the opt-in telemetry heartbeat (11:00) and a new daily data-lifecycle job (04:00) that retries Cloudflare revocations and deletes data past its retention window. ([#118](https://github.com/fellowship-dev/ready-set-mail/pull/118))
- **Sign-in codes on your instance.** Creating the owner from the setup link never asks for a code, and nobody is asked for one until a code has reached them: with the `SEND_EMAIL` binding and a sender address (the setup wizard's, or `noreply@reports.<base domain>` once it stores a base domain), each person turns codes on for themselves with **Send me a test code** in Settings → Account → Sign-in (a reset by code also does); from then on their sign-in is the password and a 6-digit emailed code. Until then, and without a sender address, sign-in is the password alone, so an instance whose tracked `wrangler.jsonc` gives it the `send_email` binding cannot lock out an owner whose address Cloudflare does not deliver to. A sign-in or test code the mail provider refuses is never reported as sent; once codes reached you, a sign-in whose code cannot be sent does not complete. `SIGNIN_CODES=off` (`vars` in `wrangler.local.jsonc`, then `npm run deploy`) turns codes off for the whole instance. ([#162](https://github.com/fellowship-dev/ready-set-mail/pull/162))
- **Migration `0013_terms_acceptance.sql`** (additive: nullable `users.terms_accepted_at` and `users.terms_version`). `npm run migrate` applies it with the others; the Worker answers 503 until the newest migration is recorded. ([#162](https://github.com/fellowship-dev/ready-set-mail/pull/162))
- **Migrations `0014_public_reports.sql` and `0015_cloudflare_import.sql`** (additive: two new tables for saved public reports; ten nullable `domains` columns, one `cloudflare_connection_zones` column and a `removed_domains` table for the Cloudflare import and its proof re-check). `npm run migrate` (or `npm run deploy`) applies them with `0013`, before the new Worker serves; the Worker answers 503 until `0015` is recorded. Saved public reports stay off until you set `PUBLIC_REPORTS_ENABLED=1`. Details: [packages/db/UPGRADING.md](packages/db/UPGRADING.md#cloudflare-import-0015).
- **Domains with an invalid `sp=`** are now read as receivers apply them (`p=none`, or no DMARC without a valid `rua=`) and say "Fix sp=": to list them on an instance before or after upgrading, see [Domains with an invalid sp=](packages/db/UPGRADING.md#domains-with-an-invalid-sp). ([#170](https://github.com/fellowship-dev/ready-set-mail/pull/170))
- **Update check.** The dashboard and the weekly digest compare your version with the latest published GitHub release and link its notes and the upgrade guide. It is a plain unauthenticated request to GitHub with no instance identifier, cached for hours; `UPDATE_CHECK=off` turns it off. ([#168](https://github.com/fellowship-dev/ready-set-mail/pull/168))

### Added

- **Connecting Cloudflare adds your domains.** On the hosted service, connecting Cloudflare adds every active zone the connection can see as a verified domain, with nothing written to DNS, and lands on the dashboard with a plain status line. If your plan covers fewer domains than there are zones, a list lets you choose which to add. A domain you removed is not added back by a later import; it is offered under Add domain, where zones that appear in Cloudflare later are suggested too (never added by themselves). Pending claims for the zones you connect are verified without a click.
- **Cloudflare accounts in Settings.** Each account is listed once with its name, its domains, whether it works, who connected it and when (and "2 connections" when two sign-ins reach it). One sign-in can cover several accounts; disconnecting it names the other accounts and says your domains stay verified and watched. With more than one account, domains carry a small account label.
- **A record of the proof.** A domain verified through a Cloudflare zone records the account, zone and time (migration `0015`: run `npm run migrate` first; see [packages/db/UPGRADING.md](packages/db/UPGRADING.md#cloudflare-import-0015)) and a `domain.proof` audit entry; it stays verified if the token is revoked later.
- **Saved, dated domain reports.** With `PUBLIC_REPORTS_ENABLED=1`, `POST /api/public/reports` runs the free domain check and, when every lookup answered, stores it as a report that anyone with its link can read (`GET /api/public/reports/:id`) and that its creator can delete with the token handed out once. Reports are kept until deleted, within a storage budget (32 KiB a report, 50 MiB a day, 1 GiB in total by default) and per-client and per-network limits. Run `npm run migrate` first (migration `0014`); limits, budgets and deletion are in [docs/data-retention.md](docs/data-retention.md#public-domain-reports). ([#169](https://github.com/fellowship-dev/ready-set-mail/pull/169))
- **Workspaces and teams.** One login can belong to several workspaces and switch between them. Owners invite people (also people who already have a login) as owner, admin or read-only member, and can transfer ownership, leave or delete a workspace. ([#107](https://github.com/fellowship-dev/ready-set-mail/pull/107), [#109](https://github.com/fellowship-dev/ready-set-mail/pull/109), [#115](https://github.com/fellowship-dev/ready-set-mail/pull/115), [#116](https://github.com/fellowship-dev/ready-set-mail/pull/116))
- **Accounts.** Email and password sign-in, plus GitHub or Google sign-in when their client ids are set. ([#109](https://github.com/fellowship-dev/ready-set-mail/pull/109))
- **Cloudflare-first onboarding.** After creating the owner you connect Cloudflare (a "Create the token in Cloudflare" link opens a pre-filled token form), pick zones and add domains; every DNS change is shown before it is written, a write Cloudflare did not confirm says "Written, not checked", and "I'll add DNS records myself" keeps the copy-and-paste path. When Email Routing rules cannot be read, the screen says why. ([#16](https://github.com/fellowship-dev/ready-set-mail/pull/16), [#163](https://github.com/fellowship-dev/ready-set-mail/pull/163), [#167](https://github.com/fellowship-dev/ready-set-mail/pull/167))

### Changed

- **A domain proven through Cloudflare can be changed through Cloudflare.** Every way a domain is verified through a Cloudflare zone (the claim's Verify button, Prove again, Add domain, bulk add, the import) now links it to the connection whose zone proved it, so Apply via Cloudflare works right away instead of answering "not linked to a Cloudflare connection". A domain waiting for verification whose zone is already in a connection's zone list is verified on your next visit to the overview, without a click: the same server-side check as before, at most once an hour per domain and five domains per visit, run for owners and admins only, and it is no longer listed as a "new domain in your Cloudflare account". A waiting domain whose zone Cloudflare grants but the zone list does not hold stays listed there: **Add** verifies it. No migration.
- **A lapse is confirmed before a proof is withdrawn.** One empty answer, an NXDOMAIN or a truncated subset of the name servers no longer takes a proof away. The daily check withdraws it only when a read at least 24 hours after the first differing one differs again (a matching read clears it); for a rival claim the same request reads twice a couple of seconds apart and, where the holder's token still works, Cloudflare's own answer must agree. Migration `0015` adds `proof_suspected_at`.
- **A stale parent proves nothing against another workspace.** A parent row stored by a 2.0 pre-release build (verified through Cloudflare, no servers) no longer admits a subdomain that another workspace holds, nor evicts that holder; one rule (an unproven row) decides what counts as proof against another workspace in every check. With no rival, a workspace's own parent still lets it add its subdomain.
- **The confirming second read uses another resolver.** For a rival claim the second read goes to dns.google (the first to cloudflare-dns.com), and `PROOF_CONFIRM_DELAY_MS` is never below 1000 ms outside tests.
- **Domains that answer are checked first.** The daily check keeps 160 of its 200 slots for domains that have answered in the last 30 days, so rows that never answer cannot delay them; the rest share 40 slots. Migration `0015` adds `proof_answered_at`.
- **"1 domain lost its proof. Press Prove again on its card."** Step 2 of the first-answer list no longer says a lost-proof domain is waiting for a DNS record that is not shown.
- **The daily check reaches every domain.** Its queue is ordered by when a row was last looked at, and every row it takes is marked, whatever the lookup answered, so domains whose lookups fail or that have nothing to compare with cannot keep a moved-away domain at the back of the queue. Migration `0015` adds `proof_attempted_at`.
- **A zone proof always has its name servers.** A domain is never stored as verified through Cloudflare without its zone and servers. Proofs made by 2.0 pre-release builds (their claim Verify button stored nothing else) count as unproven against another workspace's completed proof of the name, and the daily check records their servers when Cloudflare and public DNS agree.
- **The way back after a lost proof keeps the domain.** A domain whose proof lapsed says "Proof lost: prove it is still yours" first on the overview and on its page, with **Prove again**: it re-checks the zone through any of the workspace's connections, or the TXT record, and restores the same domain with its report history (adding the same name again does the same). The email says so and no longer advises removing it, which deleted the history. If another workspace proved the name first, it keeps it and the old history stays read-only for 30 days.
- **No report address is named unless the same action connects reports.** With Cloudflare connected but the domain's zone not in it, the DMARC step no longer shows the offered address.
- **A Cloudflare proof is not permanent.** When another workspace proves a name that a Cloudflare zone proved, the holder must show it still holds it (public DNS still delegates the zone to the name servers stored with the proof; where a token still works, Cloudflare still serves the zone in that account), or it becomes unproven and the new owner takes the name, so a domain that moved to a new owner no longer locks them out or sends reports to the old workspace. A revoked token alone changes nothing. A daily check compares public DNS with the stored servers for every zone-verified domain: when they no longer match the domain stops being accepted at report intake and the workspace's owners are emailed. Migration `0015` adds the columns.
- **The name-server check is exact.** Every NS answer must be owned by the zone name (a name that is an alias of another domain no longer borrows that domain's servers) and the public set must equal the zone's set, not a subset.
- **A full plan evicts nobody.** A holder that is replaced is detached in the same transaction as the new domain's insert, and its records, email and audit follow only once that committed.
- **Reports: no address is shown or written unless intake will accept it.** The setup status keeps `rua_address` as stored and offers the connectable address apart (`offered_rua_address`, only where Apply via Cloudflare can write it); Apply and the Cloudflare plan connect the domain before the record carrying the address is written. Without Cloudflare the record to paste has no report address.
- **Import messages are true.** A zone refused because a parent or a subdomain is verified elsewhere says so (and not who); the status line says "Nothing in your DNS was changed." (an eviction can remove the evicted workspace's own records through its connection); the import result stays on the dashboard as a note instead of a toast over the page; a domain that needs attention is listed before "Get to your first answer".
- **On the hosted service, a DMARC record Ready Set Mail writes carries your report address.** The record shown in setup step 4 and in the Cloudflare plan is the record written: the address is added beside any address already there (never dropped, never a weaker policy, never a third when two are listed), and writing it connects the domain's reports, so nothing is left to connect. Where reports are not available for your workspace the record is written without the address and the page says why. Records Apply writes itself have no Copy button, and a record is called live only after a fresh look at public DNS shows it; until then it was written and is waiting to show.
- **Cloudflare proves ownership only when it really can.** The zone must be in the connection's own Cloudflare account, the token must be able to edit its DNS, and a zone that is itself a public suffix (such as `co.uk`) proves nothing. Everything else falls back to the DNS record, as before.
- **Connecting Cloudflare from the dashboard or the first screen continues in the setup wizard** instead of returning to a "verify your domain" prompt. A waiting domain no longer hides the Cloudflare card on the first screen, and on the overview what blocks progress (a domain waiting for proof, a Cloudflare connection that stopped working) comes before "Get to your first answer".
- **New logo and colours.** The blue mailbox with a raised red flag and the "readysetmail" wordmark replace the halo envelope in the dashboard, the favicon, the PDF export, the agent consent page and the report (emails get a text wordmark, no image); brand blue `#0647FF` replaces navy and gold for primary actions, links, focus and selection, with navy `#06194B` ink. Status colours keep their meaning, and notes are now teal so they never look like an action. ([#172](https://github.com/fellowship-dev/ready-set-mail/pull/172))
- **DMARC enforcement steps follow RFC 9989.** The rollout moves `none` → `quarantine; t=y` → `quarantine` → `reject; t=y` → `reject` with explicit `p=` and `sp=`, and a step never weakens a stricter policy already published. ([#47](https://github.com/fellowship-dev/ready-set-mail/pull/47), [#106](https://github.com/fellowship-dev/ready-set-mail/pull/106))
- **DNS results say what is known.** A failed lookup is never shown as "no record", the organizational domain comes from the Public Suffix List, subdomains show the policy they inherit, and DKIM handles unknown tags, revoked keys and wildcard answers. ([#102](https://github.com/fellowship-dev/ready-set-mail/pull/102), [#138](https://github.com/fellowship-dev/ready-set-mail/pull/138), [#140](https://github.com/fellowship-dev/ready-set-mail/pull/140), [#141](https://github.com/fellowship-dev/ready-set-mail/pull/141), [#148](https://github.com/fellowship-dev/ready-set-mail/pull/148), [#158](https://github.com/fellowship-dev/ready-set-mail/pull/158))
- **The dashboard never states what it cannot show.** Missing evidence is shown as missing, not as zero or as a pass. ([#137](https://github.com/fellowship-dev/ready-set-mail/pull/137), [#138](https://github.com/fellowship-dev/ready-set-mail/pull/138), [#139](https://github.com/fellowship-dev/ready-set-mail/pull/139), [#140](https://github.com/fellowship-dev/ready-set-mail/pull/140))
- **Hosted report counting.** On the hosted service a report counts only when its mail authenticated and its sender is a known reporter; others are kept but not counted. Self-hosted installations keep counting every report (`REPORT_COUNTING`). ([#151](https://github.com/fellowship-dev/ready-set-mail/pull/151), [#152](https://github.com/fellowship-dev/ready-set-mail/pull/152), [#153](https://github.com/fellowship-dev/ready-set-mail/pull/153))
- **Sign-up, sign-in, password reset and invites end with a 6-digit emailed code.** Hosted sign-up takes an email and a password, then the code confirms the address and signs you in. Sign-in is the password and then a code, every time, on the hosted service and on a self-hosted instance that can send mail. A forgotten password is reset with a code and a new password on one screen. An old emailed verification or welcome link opens "This link is no longer used"; the retired `POST /api/auth/welcome` and `/api/auth/resend-verification` answer `410` (`link_retired`). ([#162](https://github.com/fellowship-dev/ready-set-mail/pull/162))
- **Removing a domain tells you what happened to its DNS records.** `DELETE /api/domains/:id` now answers `200 {ok, kept}` instead of `204`, listing records it left in place; the audit log records `dns.kept` and `dns.already_gone`. API clients that expected `204` must accept `200`. ([#167](https://github.com/fellowship-dev/ready-set-mail/pull/167))
- **Free-check reports** also reach senders whose own DMARC fails, replies go to `MAIL_REPLY_TO`, and each failing check comes with an exact fix. ([#125](https://github.com/fellowship-dev/ready-set-mail/pull/125))
- **The update check** compares versions properly against the latest published release (it compared with the main branch before, so it could not tell newer from older), names the version available and links the release notes and the upgrade guide. The MCP server reports the product version. ([#168](https://github.com/fellowship-dev/ready-set-mail/pull/168))
- **One DMARC record offer, never weaker than the live policy.** Every page that offers a DMARC record (DNS records, add domain, setup, connect reports, domain settings) offers the same record, keeps the live record's tags and reads `p=Reject`, `p=REJECT` and `p= reject` as `reject`. A record receivers do not apply as written (several records, a TXT that is not DMARC, an invalid `p=` or `sp=`) gets no offer; the page says what is wrong instead. ([#161](https://github.com/fellowship-dev/ready-set-mail/pull/161))
- **One SPF lookup judgement:** 10 DNS lookups are within the limit, 11 fail, on every page and in the fixes. The SPF builder never adds `all` after a `redirect=`, keeps `-all`, and the setup wizard and `POST /api/domains/:id/apply-spf` accept and refuse the same records; the route also refuses a record past the lookup limit. ([#161](https://github.com/fellowship-dev/ready-set-mail/pull/161))
- **An invalid `sp=` or `p=` is said the same way everywhere.** Following RFC 7489 section 6.6.3, receivers treat such a record as `p=none` (or ignore it without a valid `rua=`); the overview, the domain page, the DMARC wizard, the PDF and the agent tools now say so, and the first step is to fix the tag. A domain whose record has an invalid `sp=` was shown at its `p=` (or at `p=none`) before: its level changes at the next DNS refresh. ([#161](https://github.com/fellowship-dev/ready-set-mail/pull/161))
- **What a domain without reports is told.** Where reports cannot be connected (another workspace's reports on a hosted server, no report intake) the next step is "Check each service that sends as <domain>, then move to p=…", one step at a time, on the overview, the domain page, the wizard, the PDF and the agent tools alike. Hosted customers see "Reports for this domain cannot be counted yet. This is on our side; there is nothing for you to do." instead of server configuration text. ([#161](https://github.com/fellowship-dev/ready-set-mail/pull/161))
- **The overview loads with a fixed number of database queries**, whatever the number of domains (it grew with every domain without reports and could pass Cloudflare D1's per-request limit). Single-domain pages read their own summary, which now includes whether reports can be connected. ([#161](https://github.com/fellowship-dev/ready-set-mail/pull/161))
- **Settings is easier to read.** On a self-hosted instance, workspace "products" and service credentials are now an optional, collapsed **Access keys for scripts and services** section with three plain steps (group the domains, choose what the key may do in words, create the key and see how to use it); the API keeps its names. Sign out sits in the account card, leaving or deleting a workspace moved to the danger zone, revoking a key or an agent asks for confirmation, long addresses wrap in copyable fields, and the account menu shows your name and a Settings link.

### Security

- Creating the first owner requires the installer-held `BOOTSTRAP_SECRET` (or a setup link signed with it): a visitor cannot claim a fresh instance. ([#101](https://github.com/fellowship-dev/ready-set-mail/pull/101), [#130](https://github.com/fellowship-dev/ready-set-mail/pull/130), [#160](https://github.com/fellowship-dev/ready-set-mail/pull/160))
- Cloudflare tokens are encrypted at rest with `TOKEN_ENCRYPTION_KEY`; sign-in codes are stored only as keyed hashes and never written to logs. ([#113](https://github.com/fellowship-dev/ready-set-mail/pull/113), [#126](https://github.com/fellowship-dev/ready-set-mail/pull/126), [#162](https://github.com/fellowship-dev/ready-set-mail/pull/162))
- Report intake checks the sender's mail authentication and caps what it stores per address, workspace and instance. ([#120](https://github.com/fellowship-dev/ready-set-mail/pull/120), [#121](https://github.com/fellowship-dev/ready-set-mail/pull/121), [#151](https://github.com/fellowship-dev/ready-set-mail/pull/151), [#159](https://github.com/fellowship-dev/ready-set-mail/pull/159))
- Rate limits on `/mcp`, `/oauth/*` and per-address sign-in; asking for a new code needs the bot check when the instance has one; changing your password or signing out everywhere ends remembered devices. ([#145](https://github.com/fellowship-dev/ready-set-mail/pull/145), [#155](https://github.com/fellowship-dev/ready-set-mail/pull/155), [#156](https://github.com/fellowship-dev/ready-set-mail/pull/156), [#162](https://github.com/fellowship-dev/ready-set-mail/pull/162))
- Emailed codes are single use, last 10 minutes and allow 5 tries. Wrong codes are capped per address (sign-in 10 an hour and 20 a day, with a warning email to the owner at 10; sign-up and reset 10 a day) and per IP, counted atomically and only when a code was compared and wrong; the first try on a new code always counts, so a stranger cannot stop the owner who types it right, and the owner's own browser has its own reset allowance. A sign-in code is mailed only after the right password; hosted reset always needs the bot check. Sign-up creates no account until its code is right, sign-up, reset and sign-in do the same work whether or not the address has an account, and a reset request never mails an address without an account. The pending attempt lives in an HttpOnly cookie that opens nothing by itself. ([#162](https://github.com/fellowship-dev/ready-set-mail/pull/162))
- The installer's secret copies and the uninstall export are readable only by you. ([#160](https://github.com/fellowship-dev/ready-set-mail/pull/160), [#164](https://github.com/fellowship-dev/ready-set-mail/pull/164))
- Hosted accounts need a verified email, and a hosted domain is monitored only after its ownership is proven. ([#120](https://github.com/fellowship-dev/ready-set-mail/pull/120), [#121](https://github.com/fellowship-dev/ready-set-mail/pull/121), [#147](https://github.com/fellowship-dev/ready-set-mail/pull/147))
